# 游戏业务与配置规范

## Luban 导表入口

1. 当前工程的 JSON 配置必须通过 `Project/ConfigResource/gen_json.bat` 导出。
2. 必须从 `Project/ConfigResource` 作为工作目录调用脚本。
3. 禁止绕过脚本，自行拼装、复制、推测或直接执行 Luban 命令行参数。
4. 自动化执行时，可以非交互方式处理脚本末尾的 `pause`，但不得修改脚本的参数、输出目录、生成目标或数据格式。
5. 脚本缺失、执行失败或无法满足需求时，必须先报告问题并确认脚本调整方案，不得临时改用自拟命令导表。

当前 JSON 导表入口：

```text
E:\UnityTemplateTest\RaidenDemo\Project\ConfigResource\gen_json.bat
```

`gen_bin.bat` 只在明确需要二进制配置时使用，不得与当前 JSON 运行时链路混用。

## Luban 配置表格式

1. 表格顶部用于定义字段、类型、说明及嵌套关系的区域统一称为“表头定义区”，其后为“数据区”。
2. 同一张表的字体和字号必须全表统一，包括表头定义区、数据区、新增列及 Bean 展开区域。
3. 表头定义区以行为单位统一样式：同一有效行的背景色、字色必须一致，Bean 展开或合并区域不得形成局部异色。
4. 单元格以列为单位统一水平、垂直对齐方式，默认均为居中；资源路径等特殊列需要例外时，必须整列统一。
5. Bean 按字段层级展开并合并父级标题；`list,Bean` 使用多行结构，字段名前加 `*`，元素字段在下一层 `##var` 行展开。合并区域只在左上角保存内容。
6. 复制合并区域格式时，禁止从合并区域的中间或末尾单元格取样；必须从相同语义区域的左上角单元格继承。字段行、说明行、子字段行和数据行应分别从同类单元格继承格式。
7. 所有有效表头行、数据行及列表延续行必须具有与原表一致的明确线框；新增或修改单元格时，边框四边的样式、粗细和颜色必须继承同表相邻的同类有效单元格，禁止凭经验使用统一预设颜色或写死跨表通用颜色值。某个颜色值只能作为当前工作簿的已核验基线，不能直接套用到其他配置表；空白预留行不作要求。
8. 配置表格式验收禁止依赖截图、渲染图或肉眼抽查，必须直接解析最终 `.xlsx` 的单元格、样式、合并区域、批注和数据验证结构。碰撞形状核验图属于几何评审，不得用于替代表格格式验收。
9. 验收范围必须在最终文件重新打开后独立计算，禁止复用修改脚本中写死的范围。有效范围应综合字段内容、合并区域、Bean/List 结构和续行数据判断，不能只看主键列或工作表 `UsedRange`。
10. Bean/List 续行即使主键为空，只要承载子字段数据，就属于有效数据行；空白预留行不属于有效范围。
11. 有效范围内逐格核验背景色、字色、字体、字号、水平/垂直对齐、线框、文本格式和数据验证；线框必须逐边核验 `style` 与 `color`，不能只确认“存在边框”。合并区域按一个逻辑单元格检查整体样式与外边框，不要求其内部物理单元格具有独立边框。
12. 同时核验列宽、行高、合并范围和批注。`vector2`、`rect`、`pivot` 等复合值必须确认实际以文本格式 `@` 保存，不得只检查显示内容。
13. 枚举、`$type` 和 `bool` 字段必须核验下拉范围及 alias 选项；普通字段不得残留错误的数据验证规则。
14. 非明确预留区域不得残留业务内容、线框、下拉框或批注；列宽、默认字体等必要的列级属性不视为残留。
15. 每个被修改的工作簿都必须独立扫描，并输出“工作簿、工作表、单元格或合并区域、检查项、期望值、实际值”的异常清单；异常数为零才算格式验收通过。
16. 同一处理重复执行后，配置内容、结构和格式不得继续变化。Luban 导表只验证配置语义与结构，不能替代 `.xlsx` 格式验收。
17. 表格工具生成的 `.inspect.ndjson` 等核验旁路文件只能写入临时工作目录，并须在任务结束前清理，禁止进入配置表目录或版本库。
18. 修改配置表后默认只向用户列出本次涉及的工作簿及必要变更摘要，不主动打开、展示或渲染表格预览；只有用户明确要求查看时才打开对应工作簿或提供预览。
19. 已确认表结构和格式、且仅修改现有单元格值时，必须走快速增量流程：确认目标行列与当前值 → 只修改目标值 → 数据级核验 → 执行一次正式导表 → 核对生成数据。没有明确异常依据时，禁止重复扫描全表结构、样式或整个工程。
20. 纯数据修改不得重建、复制或覆盖单元格格式，也不得生成表格预览；校验应直接读取最终工作簿目标值和生成配置值。只有结构、格式、合并、批注或数据验证发生变化时，才扩大格式验收范围。
21. 同一项简单修改所需的脚本、导表与结果核验应尽量合并执行，避免能够一次完成的步骤被拆成多次串行调用。禁止为了复用一次性脚本而引入额外扫描、预览或临时产物。
22. 对外汇报耗时时，以从开始处理到最终结果返回的整轮实际耗时为准；不得只累计命令运行时间而忽略工具初始化、排队、文件处理和验证耗时。
23. 已有 Luban 工作簿禁止使用会整体重写文件的通用导入—导出流程；必须采用能够保留合并区域、样式、批注、验证、行高和列宽的原生局部修改方式。工具兼容性未经验证时，先在临时副本完成导表和格式核验，禁止直接覆盖权威文件。
24. 删除 Bean、枚举或其他连续定义块时，必须执行整行删除并让后续行自然上移；禁止用跨区域复制覆盖、清空内容或保留带格式空行来模拟删除。
25. 结构修改前必须记录目标块、相邻空行和同类块的样式基线；修改后从最终文件重新识别各定义块，不得沿用修改前的固定行号作为验收依据。
26. Bean 与枚举定义块仅保留工作簿既定颜色和粗细的完整外线框，不设置块内横向分隔线；相邻定义块之间固定保留一行无内容、无边框、无验证的空行。
27. 表头线框与定义块线框必须分别核验；逐单元格比较字体、字号、字色及四边框的样式和颜色，任何一项不一致均视为格式验收失败。
28. 枚举字段的下拉选项只能来源于该字段当前引用枚举的 `alias`；禁止从业务表已有单元格、旧数据验证公式、历史枚举项或相邻字段推导、继承、合并选项。
29. 新建或重建下拉规则前，必须删除所有与目标范围相交的数据验证规则，再为完整目标范围创建唯一规则；禁止保留旧规则并只覆盖其未占用区间。
30. 同一字段的有效下拉范围只允许存在一条数据验证规则，不得出现范围重叠、分段规则内容不一致或旧规则优先级高于新规则的情况。
31. 下拉规则修改后，必须重新打开最终 `.xlsx` 并从工作表底层数据验证集合核验：规则数量、完整生效范围、公式内容、选项顺序及旧规则残留；只检查当前单元格显示的下拉列表不算验收完成。
32. 若表格工具无法原位替换数据验证规则，必须停止继续叠加规则，改用能明确删除旧规则并建立唯一新规则的局部修改方式；不得依赖工具自动合并或覆盖行为。

## 场景背景配置

1. 场景背景资源通过独立场景配置管理；关卡只保存场景配置 ID，不直接配置各层背景资源。
2. 新增场景配置及相关资源时，只完成资源入库、Addressables 登记、场景表配置和必要校验，不得自动绑定到任何关卡。
3. 修改关卡与场景的绑定关系必须由用户明确指定。为验证临时建立的绑定，应在验证结束后恢复，并同步核对生成配置。

## 碰撞形状配置核验图

1. 新增或调整飞机、子弹等实体的碰撞形状后，应生成一张核验图供人工验收。
2. 核验图必须以实体原图为底图，按原图坐标与尺寸等比例叠加碰撞形状；碰撞形状使用醒目的绿色线框，不以半透明色块遮挡原画细节。
3. 核验图必须标出实体原点，并提供简短图例，明确绿色线框与原点各自代表的含义。
4. 多碰撞形状必须同时展示，并标注每个形状的用途或尺寸，确保能直观看出形状与机身可见区域的对应关系。
5. 核验图只用于配置评审与调试，不作为运行时美术资源，不得加入 Addressables。

## 场景管理架构

1. 战斗、关卡等场景业务应作为独立模块组织；`Model/VO` 是场景数据的唯一真相，`View/Presenter` 只负责视窗内表现的创建、同步与回收，不承载或复制业务规则。
2. 所有场景元素继承统一基类，创建时必须具有稳定唯一 ID 和明确的 Timer 类型。VO 只保存逻辑数据，不得持有 `GameObject`、`Transform`、`RectTransform`、`Image` 等表现对象。
3. 场景元素的移动、转向、战斗行为和生命周期由自身通过继承或组合负责。外部系统只协调波次、碰撞、查询等整体流程，不得以集中式 Logic 或 Panel 接管单个元素行为。
4. 场景逻辑统一由 Timer 消息驱动，不得直接读取 `Time.deltaTime`。玩家、敌方和中立场景元素分别使用 `playerTimer`、`enemyTimer`、`sceneTimer`；场景外逻辑默认使用通用 Timer。
5. Model 按 Timer 类型集中订阅并向对应元素派发时间增量，避免每个元素独立注册监听。暂停、分组变速和子弹时间统一通过 Timer 控制。
6. 逻辑生命周期与视窗生命周期必须解耦。元素离开视窗后逻辑仍可运行；View 的创建、隐藏或回收不代表逻辑元素生成或销毁。
7. 输入与界面操作只能向 Model 提交命令；Model 完成权威状态变更后通过事件通知 Presenter。View 不得直接修改 VO。
8. 场景单位原则上根据移速连续改变坐标，除非玩法明确设计瞬移能力，否则禁止直接跳变位置。
9. `view` 只放表现对象，`factory` 和 `pool` 负责对象创建与复用，`model/vo` 管理权威数据和元素行为；常量类使用 `{Module}Const` 命名。
10. 不创建空 Model、无独立职责的 Runtime 或单纯转发的包装类。一个文件只定义一个同名顶层类型；类注释使用简短 `summary` 概括角色，并以 `remarks` 说明职责范围。

## 场景资源预加载

1. 进入关卡前必须从关卡配置递归收集本局可预知的飞行物、发射器、子弹、命中特效和死亡特效资源，去重后统一预加载。
2. 配置能够确定的资源不得推迟到战斗中首次使用时加载；依赖缺失应在进入关卡前明确报错。
3. 依赖收集器只负责遍历配置和生成资源清单，不承担资源加载或玩法逻辑。
4. 预加载资源来源必须同时覆盖“配置链依赖”和“固定业务依赖”。不由实体配置直接引用、但关卡流程中可能使用的固定图片、特效等资源，应集中登记并纳入同一套校验、路径解析和去重流程。
5. 关卡表现创建图片或播放帧动画前必须确认资源已完成预加载。发现遗漏时应明确报出资源路径，禁止静默退化为关卡内临时加载。

## 场景系统与生命周期

1. 碰撞系统只负责检测并返回碰撞事实；Model 负责伤害、死亡等权威状态变化；Presenter 根据结果播放命中和死亡表现。
2. Timer 与事件监听必须成对注册和注销；战斗退出时清理 Model、Presenter、异步回调和对象池占用。
3. 池化 View 再次使用前必须重置坐标、旋转、显隐、透明度、动画和其他可变状态，禁止继承上次生命周期的表现。

## 临时测试与重构验收

- 配置归属、运行状态与执行职责必须符合已确认的设计。上层可提供上下文和生命周期许可，不得在最终执行处旁路改写所属对象的规则；临时修正应通过该对象的明确运行时接口应用。
- 对本次变更沿“配置 → 运行状态 → 实际执行”核对决策归属，不能仅凭类名、字段或文件拆分判定设计已落地。只检查受影响调用链，不因此增加全工程扫描。

1. 临时等级、血量、跳过波次等测试改动必须集中标识；恢复正式数据时同步恢复配置测试，不得保留针对临时值的断言。
2. 提交前检查临时配置、调试入口和测试断言是否一致，不得以删除失败断言代替恢复正式状态。
3. 重构完成不能只依据文件拆分或代码行数，必须确认权威逻辑已进入 Model/VO、表现引用已离开逻辑对象、冗余包装类已删除。
4. 场景架构调整后至少执行顶层类型检查、C# 编译和核心战斗流程验证。
