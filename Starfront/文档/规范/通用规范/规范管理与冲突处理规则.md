# 规范管理与冲突处理规则

状态：现行。确认日期：2026-10-22；2026-10-29修订“进规范”的执行语义。
适用范围：项目规范的读取、执行、修订和验收记录；不新增具体玩法或美术参数。

## 1. 优先关系与冲突处理

- 本规则管理项目资料内部的关系，不覆盖执行环境的系统或开发者指令。
- 项目资料按“用户明确要求 → 适用的 AGENTS.md → 项目专属规范 → 通用规范 → Skill 默认规则 → 示例”处理。先判断适用范围，再判断优先关系；历史记录仅供追溯，不作为现行执行要求。
- 用户此前已确认、且未被替代的要求持续有效。新要求只覆盖明确修改的部分；例如“上色”不解除已确认的造型、视角和尺寸约束。
- 专属规范在其明确范围内细化或覆盖通用规则，不连带取消无关约束。更深层 AGENTS.md 仅针对其目录范围生效。
- 同级规则冲突时，按明确的替代关系或授权例外处理；文件修改时间、文件名中的版本号、单纯描述更具体，均不足以证明已取代旧规则。
- 已有依据能够消解的冲突直接处理并记录。仍无法消解且影响当前任务时，只澄清冲突点；不自行选择较宽松规则，不因无关冲突停止独立工作。

## 2. 条款强度

| 标识 | 含义 |
|---|---|
| 必须／禁止 | 硬性要求；不能为方便或效果自行绕过。变更须有更高优先级依据或明确授权例外。 |
| 默认 | 没有适用的专门约定时执行；有依据的偏离需记录原因与范围。 |
| 建议 | 可根据任务取舍，不作为强制验收门槛。 |

优先关系与条款强度分别判断；低优先级文件写“必须”不会自动提升其权威。旧条款沿用原有措辞和上下文，不得因缺少标签而视为可选；有实质歧义时再澄清。

## 3. 生效状态与替代关系

- 规则状态分为“草案、现行、已替代、废止”；草案与失败试稿不得作为已通过基准。
- 修订记录至少注明日期、修改范围、确认依据，以及被替代的文件/条款。只替代注明范围，未修改部分继续有效。
- 正文维护现行规则；历史内容归档并保留替代链接。尚未迁出的历史章节必须明确标识，不与现行规则并列生效。
- 临时例外注明任务范围与结束条件；本轮试验不自动成为永久规则。

## 4. 单一来源与资料职责

- AGENTS.md 管读取入口与执行原则；通用规范管可复用方法；专属规范管项目决策；指定的数据文件管精确参数；已通过的参考图管对应视觉属性。
- 每条规则只保留一个权威来源，其他位置引用。模板维护资料与本项目运行要求分开存放、明确适用范围。
- 不笼统规定“文字优先于图片”或“图片优先于数据”。例如格子顶点以指定几何数据为准，配色与材质以已确认视觉基准为准；超出资料职责的内容不能用来推翻其他约束。
- 若指定数据与文字要求矛盾，应查明替代关系并修复，不静默选择一方。实现代码或生成图片也不能反向证明规范已变更。

## 5. 验收与维护

- 验收状态与规则状态分开记录。造型、配色、尺寸、组合效果、正式资源、运行验证分别记为“未验证、待审核、通过、暂通过、需修正”，并标明对应版本与依据。
- 用户的“通过”“效果不错”只覆盖当轮实际提交审核的项目；助手的总结不能扩大验收范围。
- 硬性要求注明检查依据：数据校验、1:1目视审核或运行验证。已读规范、生成成功、写入文档均不等于验收通过。
- 用户说“进规范”即要求对本次相关规范做整合修订，不是只追加条款。先检索现行正文、索引、引用和相关验收状态，再直接替换过时内容、合并重复项，明确废止或替代关系；正文只保留当前有效口径。
- 同步受影响的字段含义、参数说明、职责归属、读取入口与索引。按已确认归属分别维护项目与Skill；不将项目参数泛化为Skill规则，不扩大到无关文档或未授权实现改动。
- 历史记录保留当时事实与证据，标明版本及被替代部分，并链接现行来源；不能追改为当时已实现/已验收。最新已确认的验收结论必须回写到对应版本，保留尚未验证范围。
- 完成前定向检查旧术语、旧数值、失效链接和矛盾状态是否仍被当成现行要求。保留的旧内容须明确标为历史，无法消解的冲突明确报告，不静默择一。
- 完成回复精简说明新增、替换、废止了什么，以及仍有无冲突。规范更新不代表代码、资源或运行时已同步，也不默认包含Git提交或推送。
