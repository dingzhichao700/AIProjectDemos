# Group 分包与 Assets 目录原则

> 适用范围：Game Framework 模板、导出工程，以及 AIUI → Unity uGUI 的资源落地阶段。

## 一、权威顺序

发生冲突时按以下顺序执行：

1. 用户对本次任务的明确指令；
2. 目标工程根目录的 `AGENTS.md`；
3. 本专项规范；
4. Skill 默认规则；
5. 示例、历史记录与旧工程做法。

`AGENTS.md` 负责工程级决策和文档索引；本文件是目录、分包与 UI 资源落位的单一权威来源。不要在两处重复维护相同表格。

## 二、工程根目录与 Assets 根目录

```text
{GameProject}/
├── AGENTS.md
├── 文档/
│   ├── 规范/{通用规范,专属规范}/
│   └── 配置表/
└── Project/                 Unity 工程根目录
    ├── Assets/
    ├── Packages/
    └── ProjectSettings/
```

`Packages/` 位于 Unity 工程根目录，不属于 `Assets/`。

### 项目根目录治理

- 项目根目录只保留已明确归属的正式目录，例如 `Project/`、`文档/`、业务文档目录和经批准的美术生产目录。
- 禁止擅自在项目根目录创建长期存在的 `work/`、`temp/`、`output/`、`outputs/` 等笼统中间目录。
- 美术生成、处理和审核产物统一放入项目已批准的美术生产目录；正式业务产物直接写入既定目标目录，不额外复制到通用输出目录。
- 工具需要工作目录时，优先复用项目已批准的独立工作目录；该目录可长期保存制作源与成果，不按单次任务临时目录整体清理。确需单次临时目录时放在工程根目录之外，说明用途并在任务结束后按引用与保留要求清理。
- 新增项目目录前必须先确认用途、归属、是否需要进入 Git；交付前从数据层面检查 Git 状态及临时目录残留。
- 因故需要保留临时目录时，必须向用户说明其中内容、体积、保留原因和清理方式。

### 正式工程、工作目录与规范职责（2026-11-02）

- 正式工程保存运行代码、配置源表、正式入库资源与项目规范；工作目录保存制作源素材、候选稿、处理脚本、中间结果、审核及交接，不等同运行资源目录或可随意删除的缓存。
- 正式规范在工程指定的规范目录单处维护，工作目录通过链接引用；交接保存状态和证据，不另建持续编辑的规范副本。备份/快照注明历史版本，不作为现行执行入口。
- 独立工作目录默认outputs/保存成果与交付，work/保存制作过程，交接文档/保存执行记录；不混用output/outputs。此约定不允许在正式工程根目录擅建上述目录。
- 项目可声明已批准的工作目录，实际绝对路径以项目入口为准；个人工作根目录不作为通用模板常量。是否使用Git与备份方式按目录用途决定，不因Codex关联文件夹就自动初始化仓库。
- 改名、目录迁移、引用修复与历史清理执行[工作文件迁移与清理规范](工作文件迁移与清理规范.md)。
## 三、Group、目录与实际Bundle边界

### 匹配页已批准的独立最小准入（MATCHING-ADMISSION/R3.1）

用户已批准先清样例、重冻输入再最小合规迁移，不等待全库975项。该批以Manifest.matchingAdmission精确GUID/内容/meta/清单及计划SHA为准：匹配页面归Art/unpack/default/playerMatching与Prefab/default/playerMatching，专用字体材质归Art/font/fonts/material；default为兜底Group、按Label（ui_playerMatching）分包，fonts按显式条目独立。清理后消费集合44项，余14项hold（含3个未用职业Prefab），不可顺带激活。default最终组有实际入库时建立；原Default Local Group及118条目/Separate模式在迁移期原样保留，不全局重标main-content，不将本批通过等同R3全库完成。此范围内覆盖旧R2的common/uiBattle目标与旧路径例外，其他未迁记录仍按原态检查。唯一CLI精确预检、持久事务/备份/回滚、原生依赖与Editor消费自检通过后交用户验收；不删除资源、不改存档、不构建发布。


2026-11-17按用户已确认的ART-GROUP-LAYOUT/R3.1定义执行：default是未由其他明确Group管理的运行资源兜底组，内部按Label分包，不限UI或非战斗。以下为目标职责；未迁入的旧记录按Manifest精确原态保留，不因规范更新自动迁移、激活或删除。项目处于测试阶段，不维护既往体验版、底座兼容。

目录先按资源类型，再按Group及业务用途管理；Group管理构建域，Bundle决定下载粒度。静态图片按稳定ID平铺，动作/骨架保必要的角色、动作层级。atlasSource是制作输入，不是运行资源；按基础Group/业务图集名组织，与atlas产物同构。逐GUID现态、迁移范围及历史以ResourcePackManifest为准。

|Group|策略|装什么、何时加载、为何独立|
|---|---|---|
|opening|Pack Together|开场启动资源，仅启动阶段加载，隔离后续业务资源|
|title|Pack Together|标题、登录和必要加载页资源，进入标题阶段加载|
|default|Pack By Label|其余明确登记的运行资源兜底，按实际页面/用途/角色展示包按需加载；每个包保独立身份，不整组预加载|
|scene|Pack By Label|scene_{mapId}为本场景专属；scene_common_{purpose}为战斗通用，确认地图后加载，避免带入其他地图|
|cardBattle|Pack By Label|card_{cardId}为卡牌专属战斗配套，确认双方各4张后去重加载，最多8张，避免全卡加载|
|fonts|Pack Separately|按显式字体条目独立，实际消费者按需加载|
|configData|Pack Separately|按显式配置条目独立，按加载链请求|
|hotUpdate|Pack Separately|代码DLL和AOT元数据逐项独立；保hotupdate/code、hotupdate/aot别名及程序集加载顺序，按技术启动链请求|
|Built In Data|系统管理|Unity场景/Resources系统条目；不等于default，不作为Art业务分组|
|Default Local Group及其他旧Group|仅精确迁移中间态|当前未获批迁移的条目保持原态；新资源不进入旧组。腾空、消费验证并满足已批准精确删除清单后才删除|

map、battleCommon的战斗职责归scene；UI、非战斗展示、共享渲染、图标等未归其他明确Group者归default，保原用途Bundle身份。common是业务共享目录名，不再作为最终运行Group；uiMain、icons、uiCommon、renderCommon、cardDisplayAnimation等旧Group不再新增。空cutScene不保留运行组；新增过场需求再明确归属。

本次NINE-GROUPS/R3.1只迁118条目：106资源归default（8种用途包键），12技术条目归hotUpdate（Separate），23项保GUID移动，其他原位改登记。按Manifest.groupConsolidation冻结SHA、原态、目标、覆盖历史和精确写集；不迁旧Default Local Group另118项，不改变默认组指针，不激活14项匹配hold。验证后仅删迁空的9旧Group/Schema及meta共54管理文件，不删素材。旧生产器与实际消费者同批更新，关闭组由工具阻断重建。

ByLabel使用完整受控标签集合，每项仅一个Bundle身份标签，阶段/品质等不叠加为打包标签。Group合并不等于一个Bundle，也不授权整组预下载。主入口按MainPanel精确根及真实依赖加载，stageContract使用current-root-address；冻结根GUID、地址、当前Group和生产/消费源码哈希。主入口迁组须同批更新scopeGroup，不能沿用旧组猜测；旧main-content标签不是兼容目标。新增Group仅在有实际资源时创建并使用Remote Build/Load。

依赖约束：共享UI不能反向拉入整页，页面不能牵入其他页面；地图不能牵入其他地图，卡牌不能牵入其他卡牌；场景共享资源不能拉入某张卡/某地图。原生递归依赖与实际Bundle报告分别验证。已隔离且无消费者的调试材质只能按原精确GUID/哈希/证据登记为非运行根；真实运行根一旦引用它，仍接受完整依赖约束，不能创建泛化豁免。

分组事务通过同一CLI预检，核实际GUID/哈希、原Group/地址/标签及批准目标；声明全部AA设置、组/Schema、Manifest与锁文件备份。仅按批准清单更新物理路径和加载地址，保持GUID、内容与导入；技术别名不改。失败回滚，不扩大激活hold候选。逐批覆盖原生消费与依赖验证，实际提速仍须匹配版本的真机测试。

单位两源方向、新旧动作并存及专属建筑静态图按类型平铺的精确映射，统一见《资源统一治理与工具检查规范》的卡牌配套合同；不再强制为每张静态建筑图增加卡牌目录。

技能/道具源图路径`Art/unpack/default/skillIcons/{skillId}.png`、`itemIcons/{itemId}.png`继续平铺，有效运行归属为default，技能/道具分别按icons_skill、icons_item分包；ID平铺与业务关系保持。完整迁移状态、目标路径/包键以ProjectSettings/ResourcePackManifest.json为单一机器权威，业务关系仍以原Luban源表为准。

- 自动归组不得覆盖人工明确归属。新资产缺身份/模块、错误Group/完整标签集合、同GUID多条登记、待迁移行无事务切换即移动/改组均阻断；不能按任意数字目录识别地图。
- 检查显式资源及递归运行依赖，包括嵌套Prefab、静态预览Sprite、字体/Fallback、材质、Shader、图集与动态地址。只看显式组归属或只选择组内部分资源不证明下载隔离。
- 共享资源只保一个权威资产；合法派生与早期阶段受控复制按复用规范具名登记，不能仅凭像素同SHA删除。
- UI图集制作目录按`Art/atlasSource/{基础目录}/{业务图集名}/*.png`组织，基础目录为opening/title/default/cutScene/scene，业务目录内平铺；产物严格对应`Art/atlas/{同一基础目录}/{同一业务图集名}.png`。基础目录与最终目标Group对应，制作源本身不登记运行Group：default/common表示共享业务图集，default/mainView表示主界面业务图集；产物按default/ui_common、default/ui_mainView等独立Bundle身份管理。尚未迁移的产物按Manifest精确原态保留，其他业务由Manifest.atlasBusinessLayout逐项显式声明。未知业务不自动兜底；不因路径含default就重建主界面大包。此ART-BUSINESS-LAYOUT/R1选择替代旧的按AA Group搬图集源/产物路径规则，其他资源依现行域映射路由。
- common仅存真正跨模块共用素材，mainView只存主界面专用素材；队伍编辑、培养、详情、战斗/调试按实际消费者归各业务。直接作为运行散图使用的制作源，按受控批次迁入散图类型；不同时保留两份运行权威资源，不凭旧名/像素相同删除。
- UI源图不进运行登记；现有运行直接消费源图由具名旧态保留至对应批次闭合，不能用旧状态新建更多源图运行入口。
- 迁移后用实际构建报告验证未选卡/地图不被带入、无未批准重复及阶段反向依赖；用实际加载/释放验证生命周期。P0源审计不是构建或设备性能结论。

## 四、Unity 工程目录

Unity 工程位于项目根的 `Project`；项目根还必须有 `文档/规范` 与 `配置表`。Luban 配套目录是 `Project/ConfigResource`、`Project/Tools/Luban`，具体结构与路径遵循 [配置表工具链规范](配置表工具链规范.md)。

| 工程根目录项 | 作用 |
|--------------|------|
| `Assets/Art/` | UI 参考图、图集源图、图集产物、散图、动画、音频、材质 |
| `Assets/Prefab/` | Prefab，按 Group 和模块组织 |
| `Assets/Scenes/` | `GameEntrance`、`UIEditor` 等场景 |
| `Assets/Scripts/` | C# 代码 |
| `Assets/ConfigBin/` | 运行时配置 |
| `Assets/Editor/` | 仅编辑器工具 |
| `Assets/AddressableAssetsData/` | Addressables 组与构建配置 |
| `Assets/Plugins/` | 第三方插件 |
| `Assets/TextMesh Pro/` | TMP 资源 |
| `Packages/` | UPM 依赖；位于 Unity 工程根目录 |

### 纹理导入与帧动画

- 纯显示用 UI 图集和帧动画图集默认关闭 Read/Write；只有明确存在 CPU 像素读取需求时才开启。Sprite 区域引用不需要 Read/Write。
- 屏幕空间 UI 与帧动画默认关闭 MipMap；需要远距离缩小过滤的资源按实际用途单独评估，不全工程强制同一设置。
- 修改导入器时同步修正受影响资源的既有导入设置，避免规则只对新资源生效；未受影响的资源不重复导入。
- 帧动画共享图集及句柄生命周期遵循 [运行时框架与加载规范.md](运行时框架与加载规范.md)。

### TMP 字体资源

- 项目自有字体统一放在 `Assets/Art/font/`，按 `source`、`tmpFontAsset`、`materialPreset` 分别管理原始字体、TMP Font Asset 和材质预设；`source` 可继续按语言划分。
- 模板默认字体使用允许随项目分发的思源黑体简体中文版，并随字体保留 SIL OFL 许可证；禁止把授权不明确的操作系统字体复制进模板。
- 字体按阶段所需字符覆盖配置静态字库及 Fallback；Opening 基础英文字体不得隐式依赖后续阶段的大字库。其他界面按实际语言需求使用静态/动态字库，动态补字启用 Multi Atlas，避免生成单个超大全量汉字 SDF。基本英文字体的数字、标点须覆盖真实界面内容，不能机械删除正在使用的字符。
- `TMP Settings` 负责设置全局默认字体和 Fallback；已有 Prefab、场景中的显式字体及基础材质引用也必须同步迁移，不能只修改全局默认值。
- 普通文本直接使用主字体内置基础材质。描边与投影使用集中维护的 Material Preset，默认提供细描边、中描边、粗描边和描边加投影四种规格，不创建与基础材质重复的 Default 预设。
- 字体由 `TMP Settings`、Prefab 或场景引用时作为 Unity 依赖加载，通常不需要业务代码主动加载；只有运行时通过 Addressables 独立切换字体或材质时才进行显式预加载。
- 清理 TMP 默认示例字体前，必须从数据层面确认旧字体 GUID 和材质引用已经归零；`TMP Settings`、Shaders、Sprites、样式表和排版规则等 Essential Resources 继续保留。
- 禁止直接删除并重建正在被工程引用的 TMP Font Asset；重建可能改变字体内置材质的本地 `fileID`，导致 Prefab、场景或材质预设出现失效引用。确需重建时，应优先原位更新，并把引用迁移作为同一事务处理。
- 字体或材质重建后，必须从序列化数据层面核对字体 GUID、内置材质 `fileID`、Fallback 链、Prefab/场景引用及 Addressables 条目；不得只凭界面显示或资源文件存在判定完成。
- 缺字时优先补充授权明确、覆盖范围合适的 Fallback 字体；禁止为少量缺字盲目生成超大全量 CJK SDF。Fallback 资源同样需要保留许可证并纳入引用检查。
- 删除并重新创建材质后，必须检查其 Addressables 条目是否仍然存在；Unity 可能随旧资源删除同步移除原条目，需要按实际运行时加载方式重新登记。

## 五、UI 资源路径

```text
Assets/Art/UIReference/{模块}/
Assets/Art/atlasSource/{Group}/{模块}/*.png
Assets/Art/atlas/{Group}/{模块}.png
Assets/Art/unpack/{Group}/{模块}/*
Assets/Art/frameAnimation/{Group}/{模块}/{稳定ID或用途}/*
Assets/Art/skeletalAnimation/{Group}/{模块}/{美术ID}/{动作}/*
Assets/ResourceData/{Group}/{模块}/*
Assets/Prefab/{Group}/{模块}/{PanelName}.prefab
Assets/Scripts/csharp/{程序集}/{模块}/view/{PanelName}.cs
```

`{程序集}` 为 foundation、hotUpdateCore（采用共享UI分层时）、login、main 或实际子模块；旧 com/game 示例仅用于辨认历史工程，迁移规则见运行时专项规范。

规则：

- 新运行时模块名使用英文小写，例如 `bag`、`baglegendary`、`title`；mainView、cardCultivation、skillIcons等已批准模块名按统一登记保留，不为大小写对称做全库改名。制作版本、试验及退役状态进入治理记录，不作为新正式路径的组织维度。
- 模块目录按业务模块聚合，而不是按单个界面拆分。同一业务模块内的 Prefab、图集原图、图集产物、散图和视图代码必须使用同一个模块目录；例如雷电模块的 `HomePanel` 与 `StageSelectPanel` 统一放在 `default/raiden`、`atlasSource/default/raiden`、`atlas/default/raiden.png` 和 `com/game/raiden/view`，不得拆成 `raidenhome`、`raidenstage` 等界面级目录。
- 同一模块图集内的 Sprite 名必须唯一。不同界面可以继续使用相同的局部 GameObject 名（如 `imgBg`），但图集源文件/Sprite 名应带界面或语义前缀（如 `homeBg`、`stageBg`），避免合并图集时重名。
- `UIReference` 是编辑期参考资料，可使用中文展示目录；它不等于运行时模块名。
- `opening`、`title`、`default` 通常到 `{Group}/{模块}` 两层。
- `scene`、`cutScene` 可继续按 `{id}` 分目录，并与 Addressables Label 对齐。
- `shader`、`audioMixer` 等全局资源不强制按场景 id 拆分。
- 层级按资源类型约束：UI图集源图严格平铺，角色/动作/地图/Prefab components等保留必要语义层级，不把全项目统一压成两层。骨架Prefab归Prefab，骨骼纹理/动作图集归skeletalAnimation；播放JSON与PNG归frameAnimation；非Luban显示映射与编码数据归ResourceData。全局、启动和第三方结构按精确登记例外管理。
- 全项目分类、现存例外、入库/打包/登记门禁、分批纠偏及回滚遵守[资源统一治理与工具检查规范](资源统一治理与工具检查规范.md)。现存已批准特殊路径在迁移批次收口前保留，不因目标结构发布自动失效。

## 六、图集规则

### 图集原图来源与去重

- `atlasSource` 中的实际 PNG、正式 manifest 的资源声明及 Prefab 引用关系共同决定模块图集输入；Figma“组件母版”仅用于视觉核对和资源映射，不是图集本身，也不是唯一依据。
- 每个唯一视觉资源只保留一份图集原图和一个 Sprite 名称；多个独立 GameObject 可以共同引用同一 Sprite。
- 不因左右位置、对象数量或运行时身份复制相同位图。仅当像素外观或导入设置确有差异时拆成不同原图。
- 打图集前校验重复内容、重复 Sprite 名称、无引用资源及 manifest、Prefab、PNG 三者的一致性。

| 阶段 | 路径 |
|------|------|
| 源图 | `Assets/Art/atlasSource/{Group}/{模块}/*.png` |
| 产物 | `Assets/Art/atlas/{Group}/{模块}.png` |

示例：

```text
Assets/Art/atlasSource/default/bag/*.png
→ Assets/Art/atlas/default/bag.png
```

### 图集与散图分类

- 分类依据是资源的生命周期、寻址方式和图集空间成本，不依赖具体玩法、对象名称或 Figma 分组。
- 生命周期固定、随 UI Prefab 一起加载和释放的控件、装饰及图标，默认进入模块图集。
- 需要在运行时独立创建、销毁、替换、加载或卸载，且不依附固定 UI Prefab 生命周期的图片资源，默认作为 `Assets/Art/unpack/{Group}/{模块}/` 下的散图管理。
- 全屏、超大、长条或循环使用，进入图集会明显浪费空间的图片资源，默认作为散图管理。
- 新增、迁移或重新打包图片时才执行分类判断。资源及导入设置未变化时不得重复检查；优先读取正式 manifest 的已有分类，仅在记录缺失或与实际路径冲突时检查文件。
- 日常增量校验只覆盖本次变更资源及受影响 Prefab；完整模块检查只在模块图集收口、正式交付或用户明确要求时执行，不得在每个阶段全量扫描全部图片。
- 迁移 Unity 图片必须通过 `AssetDatabase.MoveAsset` 原子移动；禁止由文件系统分步移动 PNG 与 `.meta`，避免 Unity 抢先导入并重新生成 GUID。
- 对不属于本次变更且来源不明、未引用或分类存疑的存量资源，只报告并保留，未经人工确认不得自动删除或迁移。

### 图集迁移事务

- 跨阶段复制同样适用迁移事务：复制原图、重打目标图集、替换引用、更新 Addressables、旧资源清理和校验必须完整收口；删除前检查直接、间接及动态引用，失败恢复备份。
- 替换 Sprite 时核对尺寸、Border、Pivot 和 PPU；保持目标图集已有 Sprite 的 GUID/fileID 引用有效。没有 Missing Sprite 不代表显示几何与原界面一致。

- 迁移前建立受影响清单，至少包含源图、源/目标图集、Sprite 名、旧 GUID 或旧图集地址、Prefab、序列化 Sprite 字段、代码动态加载路径和 Addressables 条目。
- 执行移动前先完成预检：确认全部源资源存在、目标路径无冲突、无未处理的重复内容或 Sprite 重名、源/目标图集容量可接受，并确认目标 Addressables Group 存在。
- 迁移时把源图移动、目标图集重打、限定范围的 Prefab 引用替换、动态加载路径更新和 Addressables 登记作为同一事务；引用替换必须同时限定指定图集、Sprite 名和 Prefab，禁止全工程按名称模糊替换。
- 迁移事务任一步骤失败时必须回滚已执行的资源移动及受影响产物，禁止交付资源路径、图集、Prefab 或 Addressables 只完成一部分的状态。
- 迁出图集与迁入图集都必须重打：目标图集用于生成新 Sprite，源图集用于移除已迁出 Sprite；不得留下内容已过期的旧图集产物。
- 删除旧图集或去重源图前，必须确认 Prefab 引用、序列化 Sprite 字段、代码动态加载路径和 Addressables 引用均已处理。内容相同不代表可直接删除，先确认引用和语义归属。
- 迁移后校验旧路径/旧 GUID 引用归零、目标 Prefab 的新引用数量、全部既有图集 Sprite 内部 ID、直接源图 GUID、运行时动态换图和 Addressables 可寻址性。Player Content 构建可按当前工作流保留为独立人工步骤。

### 大背景资源

全屏背景、超大背景和循环滚动背景默认作为 `Assets/Art/unpack/{Group}/{模块}/` 下的散图，不进入 UI 图集。只有在完成尺寸、复用方式与图集容量评估并明确批准后，才允许作为图集输入。

### 动态数值进度资源

- 需要随运行时数值变化的进度显示不得把背景与当前填充值合成一张图片；至少拆分为固定背景/槽体和动态填充值两张独立位图。
- 每个进度类显示必须明确记录当前值、满状态值、满状态显示长度、最小安全显示长度、方向和运行时机制；显示比例统一按 `Clamp(当前值 / 满状态值, 0, 1)` 计算，再由满状态显示长度推导实际长度。
- 满状态显示长度必须来自已批准设计、Prefab 或显式配置，不得从可能已被运行时修改的 RectTransform 尺寸反推。窗口重开、Prefab 复用或对象池取出时，先恢复该显示基准，再按当前业务值刷新。
- 业务最大值与位图几何分离：最大值变化只改变比例，不改变批准的满状态显示长度。方向切分资源的最小安全长度只用于保护端帽；数值为零时必须采用明确空状态，不得把最小长度表现成仍有剩余值。
- 普通裁切或 `Image.Type = Filled` 使用的填充值应提供完整的 100% 视觉状态。背景或填充值也可采用按方向切分的可伸缩原图：横向伸缩只设置左右 Border，并保持位图高度与 Image 高度一致；纵向伸缩只设置上下 Border，并保持位图宽度与 Image 宽度一致；只有横纵两个方向都明确允许伸缩时才设置四边 Border。原图在伸缩方向上的长度无须等于最终显示长度，但必须记录不允许端帽或圆角互相挤压的最小安全尺寸。
- 图集打包必须把源 Sprite 的 Border 原样写入最终图集 Sprite，并在打包后校验 Border 一致；不得只在 Prefab 或设计说明中记录九宫格意图。
- 固定背景默认不进入 UIBinder；只导出运行时需要控制的填充层。采用方向切分填充时，通过改变填充层在进度方向上的长度、遮罩或分段结构表达数值，垂直方向尺寸保持不变；不得继续使用会裁掉必要圆角端帽的方式。
- 正式 manifest 应分别记录背景和填充资源、显示区域、内边距、方向、初始值、Border、最小安全尺寸及实际运行时实现方式。

操作要求：

1. 在 Unity Project 中选择 `atlasSource` 下的叶子文件夹。
2. 使用 `Assets → UI工具 → 合并图集`，或“合并图集（保留透明）”。
3. 不在工程外单独调用 TexturePacker 拼图集。
4. 产物目录只保留 `{模块}.png`、`.meta`，不得残留 `.tpsheet` 或多余目录层级。
5. 图集工具读取不到刚新增或迁移的源图时，应对该资源执行一次同步导入后重试；不得要求重复运行整套打包流程。
6. 源图名称集合必须与图集 Sprite 名称集合一致。
7. Prefab 或图集变化后，重新登记并构建 Addressables。
8. 同一模块包含多个 Prefab 时，应将这些 Prefab 作为一个模块批次完成收口：图集只打包一次，再统一替换和校验全部 Prefab 的 Sprite 引用；不得按界面重复生成内容相同或职责重叠的模块图集。

透明边界规则：

- 资产本身不应包含无设计意义的透明空边；应在进入 Figma/Unity 前清理。
- 需要保持 Figma 像素坐标、九宫格边界或设计留白时，打图集使用“保留透明”。
- 不依赖打图集时的 Trim 来修复按钮两种状态视觉边界不一致。

## 七、UI Prefab 落地规则

### AIUI 结构化导出

AIUI 流程在 Figma 验收后直接生成完整视觉层级，不属于传统的“空壳 Phase1”。

- Figma 是最终层级、坐标、文本框与资源摆放的权威来源。
- 图片默认使用 `UnityEngine.UI.Image`。
- 文本默认使用 `TextMeshProUGUI`，保持单行、固定设计宽高和明确位置。
- 带文本的按钮中，文本 RectTransform 不得直接拉伸为整个按钮尺寸；其高度只需略高于字号，并在按钮内按设计位置纵向居中。
- 同组状态按钮默认保持相同尺寸和视觉边界。若设计指定“仅通过文字表现选中态”，所有状态必须复用同一按钮图片，仅改变文字颜色、字号或已确认的文字效果。
- 自定义交互组件在 Unity 导出阶段映射。PoC 可暂用 `UnityEngine.UI.Button`；生产导出若工程要求 `GameButton`，必须在用户确认其类型和序列化字段后替换，不得猜测。
- 组件与脚本必须存在明确的运行时消费者或 Unity 强制依赖；不得为了“以后可能会用”而在根节点、按钮或普通视觉节点上预防性挂载 `CanvasGroup`、行为脚本或其他组件。整窗淡入淡出、统一交互开关、射线控制等需求未被结构或功能逻辑明确声明时，根节点只保留实际必需组件。
- 自定义控件只能附加其当前实现真实读取的依赖。字段仅被获取但从未参与逻辑，不构成组件挂载依据；导出后应校验组件数量，并清除已确认无消费者的冗余组件。显式需要的动画、状态或交互组件必须记录用途，不得被通用清理误删。
- Figma 审核产生的改动不静默回写 Blueprint，应记录在 handoff/export manifest。
- 非拉伸位图采用一比一尺寸链：高保真成图中的可见宽高、独立 PNG 像素宽高、Figma 组件母版与生产实例宽高、Unity `Image` 宽高必须使用同一组整数。图像模型输出的任意超采样不得原样流入图集；应在资源定稿时按生产尺寸归一化一次。
- 九宫格/方向切分、平铺、填充、遮罩和循环背景等明确可缩放资源可以让原图尺寸与显示尺寸不同，但必须在正式 manifest 中记录缩放机制、原图尺寸、显示尺寸与 Border；未声明的尺寸差异一律视为异常。
- 点击热区需要扩大时使用独立父级命中区域，不得通过放大位图画布、增加透明留白或缩放生产图片实现。
- Prefab 中所有节点的 `RectTransform` 坐标、宽度和高度必须为整数；Figma 到 Unity 的转换在边界处统一取整，并在序列化后检查，不得把小数留给人工清理。
- 普通 UI 节点用职责前缀加语义的小驼峰名称，如 boxToolbar、btnEditTeam、imgPowerBg、txtOwnedCount。重复项用业务含义或槽位编号区分。预制体根节点沿用预制体／类名，ScrollList 的 Viewport、Content 使用固定大小写。按每个节点自身职责命名。例如数量控件的容器用 boxOwnedCount，显示数量的文本用 txtOwnedCount。
- 导出配置保存设计图层到 Unity 节点名的映射，用稳定图层标识或可区分的层级路径定位，重复导出时复用。导出前检查职责前缀、同级重名及缺乏业务含义的生成序号。
- 改名时逐项核对 Prefab 序列化对象引用、UIBinder 成员与目标、运行和编辑器代码中的字符串路径。通过实际界面入口验证受影响交互；涉及列表时检查滚动复用和条目点击。纯改名可比对 Prefab 差异，核实变更仅涉及名称。
- 进度类控件按职责命名：整体容器使用 `bar{语义}`，背景图片使用 `img{语义}Bg`，动态填充图片使用 `img{语义}Fill`，数值文本使用 `txt{语义}`。容器被运行时控制或绑定时仍使用 `bar{语义}`，不得以某个子图片的 `img...Bg` 名称代替整体结构。

### 传统空壳流程

仅当任务明确要求传统 Phase1 时，才生成空壳 Prefab、空壳脚本与 `UIBinder`；不要把该要求套用到已经完成 Figma 验收的 AIUI 完整导出。

### UIBinder 成员导出

成员导出遵循“人工决定范围、工具执行生成、最小必要集合”的边界：

- 导出会被运行时代码直接操作的交互节点，如按钮、可点击文本或容器。
- 导出需要动态控制内容、状态或显隐的节点，如 `ScrollList`、动态 Sprite、品质框和状态文本。
- 纯静态背景、标题和装饰默认不导出；只有确认存在运行时控制需求时才加入。
- `ScrollListItem` 的静态槽位底图默认不导出；物品图、品质表现等动态节点按实际需求导出。
- 人工负责确认最终节点集合；自动化可以在用户确认后配置 `uiList` 并执行生成，不得自行扩张成员范围。

生成必须复用目标工程 `UIBinderInspector` 的“一键生成绑定”逻辑，不得另写一套字段文本生成器。该生成动作必须：

1. 根据真实组件类型自动补齐所需命名空间，例如 `Image` 对应 `UnityEngine.UI`、TMP 文本对应 `TMPro`。
2. 保留生成标记之外的用户代码，不覆盖业务逻辑。
3. 对 `ScrollListItem` 模板同步同级编辑期预览克隆的 `UIBinder` 配置，并按模板内相对路径重建引用，避免对象池首次复用旧克隆时成员为空。
4. 完成后验证模板与全部池化克隆的成员数量、类型和引用均一致，并验证 Unity 无编译错误。

### ScrollList 编辑期预览 Item 数量

#### 固定结构、组件与布局

- 列表根节点按 `list{语义}` 小驼峰命名，固定挂载 `ScrollList` 和 `ScrollRect`。层级固定为 `listXXX → Viewport → Content → Item模板`，`Viewport`、`Content` 保留该大小写名称；禁止让根节点兼任 Viewport。
- Viewport 挂载 `Image + Mask`，关闭 Mask 的 `Show Mask Graphic`，Image 开启 `Raycast Target` 以覆盖列表交互区域。不能用根节点上的 RectMask2D 替代此结构。根节点的 Image 仅在实际需要列表背景时添加。
- Viewport 的 anchorMin=(0,0)、anchorMax=(1,1)、pivot=(0,1)，四边偏移为0；拉伸铺满列表根节点。
- Content 的 anchorMin、anchorMax、pivot 均为(0,1)，初始 anchoredPosition=(0,0)，尺寸由 ScrollList 管理。不得额外挂 LayoutGroup 或 ContentSizeFitter 与其竞争布局控制。
- Item 模板采用左上角锚点及 pivot=(0,1)，初始 anchoredPosition=(0,0)，配置明确的宽高供布局计算。是否配置 UIBinder 和 ScrollListItem 派生脚本取决于实际展示需求，不一律强制。
- ScrollRect.viewport 指向直接子节点 Viewport，ScrollRect.content 指向其子节点 Content；ScrollList.itemTemplate 指向 Content 下唯一的权威模板。ScrollRect 横向、纵向仅启用一种，并配置对应的行列限制。
- 验收必须检查层级、组件所在节点、RectTransform 布局和引用目标，不能以“引用非空”或“编译通过”代替结构验收。改名或更改绑定类型后，用现有 UIBinder 生成器同步字段，保留生成区外代码。

#### 预览数量

- `ScrollList.itemTemplate` 原则上只指向一个权威模板节点；数量可变的是同级编辑期预览或对象池 Clone。
- Prefab 中预生成的 Clone 不规定固定数量，不得把示例中的 50、100 等数量写成通用验收常量。
- 数量应足以检查视窗内的行列分布、间距、边缘和视觉还原；可为滚动衔接保留少量超出可见容量的 Item。
- 按 ScrollList 视窗尺寸、Item 尺寸、横纵间距和行列限制估算可见容量。若预生成数量明显超出视窗可容纳数量，且没有明确的对图或调试目的，应减少，以免增加 Prefab 体积、序列化、导入和初始化开销。
- 运行时数据总量与 Prefab 预生成数量解耦；较大的数据集应由 ScrollList 的对象池和滚动复用处理，不要求在 Prefab 中持久化等量 Clone。
- 人工为对比效果图临时增加预览 Item 合法，但交付 manifest 必须记录实际数量和用途。
- UIBinder 生成与校验必须遍历当前保留的全部模板和 Clone，确保成员数量、类型和引用一致；不得硬编码 Clone 数量。

### 阶段交接时看哪些文件

- `run.manifest.json` 是整个任务的总交接单，下一阶段优先读取。
- `unity/export.manifest.json` 是 Unity 阶段的详细交接单。它与总交接单共同组成当前正式交付记录。
- `Library/AIUI/*.export.json` 只是工具运行时的检查报告，可用于排查问题，但不是正式交接单。
- 名称包含 `pre-`、`backup`、`failed` 的文件或目录是历史快照，不代表当前结果，默认不得据此验收。

交接时遵循以下规则：

1. Prefab、代码、资源或成员绑定发生变化后，当前阶段必须同步更新两份正式交接单。
2. 正式交接单应记录实际数量、用途、成员导出状态、成员集合、验证结果和关键文件哈希。Stage 8 完成后不得继续记录“成员稍后导出”或空成员状态。
3. 下一阶段先核对交接单与实际 Prefab、代码和资源。两者一致时按交接单继续；不一致时以实际产物为事实来源，把交接单视为过期并先完成信息对齐。
4. 每个阶段结束时只保留一套明确的当前正式交付结果，不得让下一阶段在多个 JSON 或历史备份中猜测哪个最新。
5. 条件允许时，正式交接单写入 `artifactRole: handoff`、`authoritative: true`；临时检查报告写入 `artifactRole: diagnostic-execution-report`、`authoritative: false`。

ScrollList 数量必须分开记录：`itemTemplateCount`、`previewCloneCount`、`itemBinderCount`，以及已知时的 `runtimeDataCount`。不要用含糊的“Item 数量”代替；运行时数据量与 Prefab 预览数量无关。

一句话原则：**正式交接看 manifest，实际状态看 Prefab 和代码；两者不一致时先对齐，备份文件和 Library 报告只用于排查问题。**

## 八、最小验收

- Prefab、图集源和图集产物路径符合本规范。
- 图片和 TMP 文本数量、节点层级与批准后的 Figma 一致。
- 文本框没有被错误拉伸到按钮全尺寸。
- 图集 Sprite 名称、数量、透明边界和九宫格 border 正确。
- Prefab 与运行时图集已进入正确 Addressables Group；编辑期资源未进包。
- UIBinder 成员只包含人工确认的运行时必要节点；生成类 import 完整，列表模板与池化克隆绑定一致。
- ScrollList 只保留一个权威 Item 模板；预览 Clone 数量与视窗容量和校验目的相称，manifest 记录实际数量且验收不依赖固定值。
- 正式交接单与当前 Prefab、代码、资源及成员状态一致；Library 报告和历史快照未被误作当前交付结果。
- Addressables Player Content 已在资源变更后重新构建。
