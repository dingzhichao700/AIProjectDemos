# 自包含模板与导出规范

## 一、独立性的定义

普通导出只允许读取本仓库的 `Templates/GameFramework/ProjectFiles`，不得读取或克隆其他 Unity 工程。Unity Editor 与 Unity Package Registry 属于外部软件依赖；TexturePacker 的标准版本由本仓库 `ThirdParty/TexturePacker` 管理，并在导出时部署到样例工程的 `Project/Tools/TexturePacker`。

`ProjectFiles` 不要求作为日常工程直接打开，但必须包含复制后生成一个有效 Unity 工程所需的全部源文件。

## 二、模板结构

模板还必须包含 `RootFiles/文档/配置表`、`ProjectFiles/ConfigResource`、`ProjectFiles/Tools/Luban` 及锁文件。导出时 `RootFiles` 复制到工程根目录，仓库 `docs` 映射到工程 `文档/规范`，并转换根目录 AGENTS 的链接。完整契约见 [配置表工具链规范](配置表工具链规范.md)。

```text
Templates/GameFramework/
└── ProjectFiles/
    ├── Assets/
    ├── Packages/
    │   ├── manifest.json
    │   ├── packages-lock.json
    │   └── com.code-philosophy.luban/
    └── ProjectSettings/
```

仓库不保存 Addressables 预构建缓存。`ProjectFiles/Assets/AddressableAssetsData` 是配置的唯一权威来源。

## 三、模板禁止项

- Unity 生成目录：`Library`、`Temp`、`Logs`、`UserSettings`、`obj`。
- IDE 产物：`.vs`、`*.sln`、`*.csproj`。
- 单次实验产物：bag、bagcartoon、baglegendary、shop、UIReference、AIUI 临时生成器。
- 外部工程路径、Golden/b1 克隆逻辑和机器专属默认路径。

## 四、导出契约

1. 运行模板静态验证。
2. 在系统临时目录建立 staging，不在最终目录制造 baseline 或中间工程。
3. 复制 `ProjectFiles` 到 `{ProjectName}/Project`。
4. 从仓库 `ThirdParty` 部署已锁定版本的开发工具到工程 `Project/Tools`。
5. 写入项目名称、AGENTS、docs、README 和 gitignore。
6. Unity 第一遍完成导入与编译。
7. Unity 第二遍执行 `GameFrameworkExportPipeline.ExportBaseline`，初始化并构建 Addressables。
8. 检查编译日志、成功 marker 和 bundle。
9. 全部通过后清理 `Library` 中可再生的导入与编译缓存，仅保留 `Library/com.unity.addressables` 的已验证构建产物。
10. 把瘦身后的 staging 移到最终输出路径。

目标已存在时默认失败；只有用户明确授权后才能使用 `-Force`。

## 五、TexturePacker 工具管理

- TexturePacker 的标准版本统一存放在 `ThirdParty/TexturePacker/{version}/{platform}`，不得依赖开发者个人目录。
- 导出器必须先校验标准工具源完整，再部署到样例工程的 `Project/Tools/TexturePacker/{platform}`；缺少主程序时立即终止并报告确切路径。
- Unity 编辑器工具优先解析工程内相对路径。`EditorPrefs.TexturePackerExePath` 只在工程副本缺失时作为人工兜底，不得保存 Skill 仓库绝对路径作为工程依赖。
- 升级时新增明确版本目录，并同步修改导出器锁定版本及验证规则；禁止静默覆盖既有版本。
- 工具目录应保留命令行程序运行所需的完整依赖，不得只复制单个可执行文件；不得提交个人许可证、密钥或机器状态文件。

## 六、Addressables 现场构建

每次导出都必须调用 Unity，根据当前 `ProjectFiles` 初始化、登记并构建 Addressables。不得提供跳过构建的参数，也不得复制旧的 `AddressableAssetsData`、catalog、settings 或 bundle；构建失败即导出失败。

Addressables 构建和编译验证必须在 staging 中真实执行，不能为了缩小交付体积而跳过。验证完成后，导出器应删除 `Library/BuildCache`、`Artifacts`、`PackageCache`、`Bee`、`ScriptAssemblies` 等 Unity 可再生缓存，仅保留 `Library/com.unity.addressables`。接收方首次打开工程时由 Unity 重新生成编辑器缓存。

上述要求针对“生成完整样例工程”的正式导出。已存在工程内的 AIUI 日常预览不属于完整工程导出：预览只同步变化的位图并生成可视 Prefab，不打图集、不登记或构建 Addressables，也不增删临时 C# 导出器。视觉定稿后再执行图集与绑定，发布校验时才登记并构建 Addressables；经用户确认，发布构建可留作人工步骤。

模板常驻 `Assets/Editor/AIUI/AIUIExportQueue.cs`，通过 `Library/AIUI/pending-preview.json` 接收预览请求。安装或升级工具本身允许发生一次编译和 Domain Reload；后续请求不得通过修改 `Assets` 下的脚本来触发执行。位图内容及导入设置未变化时，不得重复复制或调用 `SaveAndReimport`。

AIUI 定稿通过同一常驻工具的 `Library/AIUI/pending-finalize.json` 一次完成打图集、Prefab Sprite 引用替换和结构校验，并以 `finalize-result.json` 的状态与耗时作为完成依据。图集迁移应分别记录一次性工具编译、资源移动、源/目标图集重打、引用替换与校验耗时，不得把工具升级等待混入日常迁移耗时。不得使用 `Assets` marker 或解析 Editor.log 判断完成；请求 5 秒仍未消费时立即检查 runner/导入状态。普通内容定稿不重复执行 Skill 或完整模板校验，只有工具、模板或规范发生变化时才执行。

## 七、标准化回写

外部样例工程只在“标准化回写”中作为一次性、已验收的差异来源。回写前逐项确认可复用性；回写后运行静态验证，并在需要时从模板重新导出工程完成 Unity 验证。

禁止把游戏开发的定制化产物标准化回写，包括具体模块的资源清单、Prefab、业务代码、配置数据、模块名、图集名、资源名、目录实例、GUID、fileID、Addressables 条目或地址，以及单次请求、报告、测试数据和耗时结果。只允许回写从已验收产物提炼出的通用规则、参数化工具能力和不携带项目数据的实现。

- 修复资源迁移或生成逻辑时，同时审计模板已有资源及引用，禁止只停止错误生成而保留错误基线。按模板自身输入重新生成并验证，不复制样例专属图集、Prefab 或引用标识。

## 八、验收标准

- 隔离或重命名所有外部样例工程后仍可导出。
- 新工程包含完整 Assets、Packages、ProjectSettings 和内嵌 Luban。
- 新工程包含六张基础 Excel、ConfigResource 配套目录及锁定 Luban 生成器；独立 JSON/bin 导表验证通过，且 staging 内实际 JSON 生成成功。
- 新工程包含可独立运行的 `Project/Tools/TexturePacker`，图集工具无需访问仓库或个人目录。
- Unity 编译与 Addressables 构建成功。
- 没有 Missing Script、Missing Sprite 或样例专属资源。
- `docs/docs` 不存在。
- `GameEntrance → Opening → Login → Option → Loading → Main` 可正常运行。

## 九、启动初始化顺序

`RookieEngine.Awake` 先建立 UI 根、Timer 和对象池等核心服务，再启动 GameEntrance。资源系统及 Login 程序集就绪后，LoginEntry 读取本地设置并执行 SettingControl.ApplyAllSettings，最后打开 Opening。设置模块留在 Login，Foundation 不编译引用业务设置类；新存档和已有存档均应用一次完整设置。


## 十、平台策略及标准化回写验收

- 模板是新项目的原始工程来源。通用能力遵循 [运行时框架与加载规范.md](运行时框架与加载规范.md)，选择微信小游戏平台时默认执行 [微信小游戏平台规范.md](微信小游戏平台规范.md) 的完整方案；其他平台单独定义执行策略。
- 平台选择必须明确。普通模板导出与微信小游戏导出不是同一验收结果；不能因为导出 WebGL 成功就宣称 HybridCLR、远端发布及微信真机通过。
- 可复用实现回写范围：Timer/Handler、共享图集帧动画、异步资源加载、UIBinder 绑定和类型解析、纹理导入、舞台自适应、通用输入及模块化启动。回写时迁移必要依赖，保持模板自身序列化引用，不整体复制样例目录。
- 微信策略实现须同步具备程序集配置、启动入口、DLL/AOT 加载、地址映射、版本契约和平台缓存集成；不能只复制 Foundation 加载器而遗漏构建侧约定。具体构建发布脚本和 Jenkins 由后续独立工作维护。
- 不迁入样例的实际 CDN 地址、AppID、底座/内容标识、生成的 DLL/AOT、发布目录、美术及业务资源。所有项目实例信息由导出或项目配置提供；微信 SDK/HybridCLR 版本及许可依赖需要显式管理。
- 测试源码和脚本统一放入既有 Tools，产物写入 Library 或可识别系统临时目录。构建和 HybridCLRData 等可再生目录进入 Git 忽略；与底座绑定的历史构建资料仍需单独归档。
