# 游戏业务与配置规范

> 适用范围：基于模板开发的游戏业务模块，以及 Luban 配置从生成数据到运行时业务数据的接入。

## 一、业务 Model 与 VO

- 仅当模块存在业务数据管理需要时，才建立与模块同名的 `{Module}Model` 作为主要数据管理入口；不得为满足目录形式机械创建空 Model。
- 当数据管理职责过大、集中在一个 Model 中容易混淆时，可以按明确业务职责增加其他 Model。
- 单条业务数据对象命名为 `{Semantic}VO`，文件统一放入模块的 `model/vo/` 目录。
- Control 负责业务流程和权威状态修改；Model 负责数据集合、查询、初始化与存储边界；View 不直接修改 VO。
- 模块内固定常量类统一命名为 `{Module}Const`，例如 `BattleConst`；不得继续使用含糊的 `PrototypeConfig`、`CommonConfig` 等名称承载模块常量。

## 二、Luban 配置分层

原始工作簿、生成器、脚本及路径均为工程必备开发内容，按 [配置表工具链规范](配置表工具链规范.md) 交付与验收，不以运行时包替代生成工具。

- `CfgManager` 是统一运行时入口，负责使用 Addressables 已预加载的 JSON 或 bytes 初始化 Luban `Tables`、暴露表集合并在清理时释放资源。
- 仅当某张或某类配置存在重复使用的二次查询需求时，例如按类型取得配置列表，才在 `com/game/config/mgr/` 建立辅助管理类；不得为每张表机械创建 `CfgMgr`。
- `config/mgr` 只负责查询、筛选、索引或组合 Luban 原始映射对象，返回值仍应是 Luban 映射对象。
- 将配置转换为业务 VO、结合运行时状态构建玩法数据或实现玩法规则的逻辑，属于对应业务模块的 Model。

## 三、运行时加载顺序

1. 将所有需要运行时读取的 Luban 无扩展名配置名称登记到 `ResourceConst.ALL_CONFIG_LIST`。
2. 在平台规定的阶段通过 Addressables 将列表中与 Tables 构造函数匹配格式的数据全部预加载到 `ResourceManager` 缓存；微信平台在 LoginPanel 打开时执行，不再放入 Opening。允许有上限并行，全部成功后才初始化。
3. 预加载完成后调用 `CfgManager.Init()` 创建 Luban `Tables`。
4. 业务模块只能在初始化完成后读取 `CfgManager.tables`；过早读取或缺少预加载资源必须显式报错，不得静默回退到磁盘或空数据。

## 四、新表接入流程

1. 设计并创建业务工作簿，登记到 Luban 总表。
2. 使用工程既有 Luban 导表脚本生成 C# 映射类和配套 JSON 或 bytes，不手工修改生成文件。工程提供 `gen_json.bat`、`gen_bin.bat` 等脚本时，必须从脚本预期的工作目录调用对应脚本；禁止绕过脚本自行拼装、复制或推测 Luban 命令行参数。
3. 将当前格式的生成数据注册到正确的 Addressables Group，并加入 `ALL_CONFIG_LIST`；微信平台统一进入 configData，采用 Pack Separately，不归入 title。
4. 验证生成文件、配置记录数、主键查找和代表性字段读取。
5. 按职责决定直接读取映射对象、建立按需 `CfgMgr`，或在业务 Model 中转换为 VO。

项目专属表结构、数值、业务 VO、玩法规则、测试断言和 Addressables 条目不得回写模板。

自动化调用带 `pause` 的批处理脚本时，可以非交互方式向脚本提供继续输入，但不得修改脚本参数、输出目录、生成目标或数据格式。脚本缺失、失败或与当前需求不匹配时，应先报告并确认脚本调整方案，不得临时改用自拟命令完成导表。

JSON/bytes 自动识别、统一资源加载、失败重试及格式切换验收遵循 [配置表工具链规范](配置表工具链规范.md)，不得退回直接调用固定格式 Tables 构造函数的实现。

## 通用常量配置


1. 通用常量统一使用 `ConfigValueResource`，字段结构为 `id + type + valueType + content`。`type` 只区分普通值、列表和 Map；`valueType` 只区分字符串、整数和浮点数。
2. `content` 在 Luban Schema 中始终声明为 `string`，并在 Excel 中按文本保存。具体数据类型由运行时根据 `type + valueType` 严格解析，禁止依赖 Excel 自动转换推断类型。
3. 列表与 Map 只支持单层、同类型数据，不支持嵌套集合或混合值类型。Map 键固定为区分大小写的字符串，`valueType` 只描述 Map 值类型。
4. 集合分隔、转义、空内容、空元素、空键、重复键、数值格式和表示范围遵守 [`常量表配置规范.md`](常量表配置规范.md)。解析失败必须明确报错，禁止静默返回 `0`、空集合、空字符串或其他默认值。
5. 业务代码统一通过 `ConfigValueHelper` 获取类型化结果，不得直接访问或自行解析 `ConfigValueResource.Content`，避免同一配置在不同业务模块产生不同解释。
6. `ConfigValueHelper` 必须严格校验请求的结构类型和值类型，不执行整数、浮点数、字符串之间的隐式转换。列表和 Map 只允许 `int`、`float`、`string`，并通过只读接口返回。
7. Helper 只缓存成功解析的结果；类型不符、格式错误、数值越界和其他失败结果不得进入缓存。缓存命中前仍须校验请求类型，防止同一 ID 通过错误接口取得已有对象。
8. 常量配置属于只读加载数据，解析缓存跟随配置生命周期：`CfgManager.Init` 和 `CfgManager.Clear` 必须清空缓存，避免重新加载配置后继续使用旧结果。
9. 正式业务使用的常量必须在对应业务常量类中定义为具有业务含义的静态属性，通过 `ConfigValueHelper` 单行读取，并在属性上方添加说明注释。禁止额外创建只保存配置 ID 的类、增加业务层重复缓存，或在多个调用点散落裸数字。
10. 常量配置 ID 按业务划分号段，细分业务按百位段连续编号并预留扩展空间；ID 只表达业务归属，不编码数据类型。号段分配必须登记在填写说明中，并写入配置表表头 `id` 字段的批注；号段调整时两处同步更新。
11. 描述统一使用“业务前缀_具体含义（单位）”，同一业务只使用一种前缀。时间、距离、速度等有量纲的配置必须明确标注单位。
12. 原始配置保持只读；数值边界在最终业务生效位置处理，不得为了满足边界而提前改写源配置。读取或解析失败必须明确报错，禁止静默使用默认值。
13. 有意设置的越界值、非法格式等配置测试数据，必须在描述列标明测试意图。此类数据由预期失败用例验证，不得为了让所有行都能成功解析而擅自修正。
14. 新增全局配置表时，必须同步完成 Luban 表注册、正式脚本生成、配置预加载清单和 Addressables 登记，并验证代表性数据能够沿正式加载链路读取。
15. 常量配置测试只维护示例 ID `1～8` 的存在性要求，不重复维护全部业务配置 ID。测试必须遍历整张常量表，根据 `type + valueType` 调用对应读取接口；解析成功后打印内容，不断言具体配置值；故意非法的数据单独登记为预期失败样例。
16. 常量配置测试必须检查重复 ID、不支持的类型组合和内容解析失败，并在全部配置检查结束后统一报告错误，避免首个错误阻断后续结果。Helper 的独立测试继续覆盖接口类型校验、缓存复用、配置生命周期清理、集合只读及转义边界。


ConfigValueResource 是跨项目基础表，连同读取 Helper 和示例随模板交付，不归入禁止回写的项目专属业务表。具体业务号段及数值由各项目维护，模板不复制样例项目的业务常量。

项目专属约定见[功能开启配置规范](../专属规范/功能开启配置规范.md)。
