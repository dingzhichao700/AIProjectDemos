# 微信小游戏平台规范

> 适用范围：模板选择微信小游戏平台时的默认执行策略，以及已采用该策略的派生工程。HybridCLR、远程资源加载、版本与缓存作为一套完整方案执行，不作为零散可选建议。其他平台使用各自策略，不由此推定所有平台必须采用相同发布机制。
>
> 本规范源于雷电战机已通过开发者工具及真机验证的链路，规定后续模板实现与构建系统共同遵守的契约；模板通过显式平台选择启用对应源码、固定版本依赖及构建入口。实现回写状态见 [模板与导出规范.md](模板与导出规范.md)。

## 一、程序集与 HybridCLR

| 部分 | 归属及加载方式 |
|---|---|
| Foundation | AOT 底座；负责启动、资源及模块加载，不加入热更新程序集列表 |
| Login | 热更新程序集；按目标平台编译后作为 `.dll.bytes` 经 Addressables 装载 |
| Main | 热更新程序集；正式内容入口之前装载 |
| SubModule | 有实际业务时新增，按依赖顺序和使用阶段装载 |
| Editor | 仅编辑器使用，不进入 Player |

- `.asmdef` 定义编译边界；HybridCLR 的热更新程序集配置决定哪些程序集从 AOT 编译中排除并以 DLL 发布。Foundation 有 `.asmdef` 仍然属于底座；没有加入热更新列表的 Player 程序集按 AOT 构建及裁剪规则处理，并非保证所有代码都原样保留。
- 业务程序集不得形成环形依赖，Login 不得引用尚未装载的 Main。主程序集和子模块的公共类型归属必须明确，禁止通过反向引用破坏阶段边界。
- 热更新 DLL 必须由与实际底座兼容的 Unity、HybridCLR、目标平台和编译配置生成；不能把任意 Editor DLL 改后缀当成正式热更新产物。
- AOT 补充元数据来自对应底座的裁剪后程序集，按需经 Addressables 下载；它不是替换 AOT 本机代码的热更新 DLL。需与该底座产物配套归档，不得混用其他底座生成的元数据。
- 先补充必要 AOT 元数据，再加载业务 DLL，最后调用业务入口或创建相关界面。下载可有限并行，元数据装载按清单顺序执行并检查返回结果。
- 编辑器使用已编译的业务程序集，不重复 `Assembly.Load` 同名 DLL；编辑器能运行不代表真机热更新链路已通过。
- 已加载的业务 DLL 不尝试在同一进程内替换，新内容通过重新启动生效。一次启动锁定同一底座及内容版本，不在进入 Main 时重新选择另一个版本。

## 二、资源归属与启动阶段

- Addressables 管理的业务资源、热更新 DLL 和 AOT 元数据统一使用 Remote Group。Group 是资源归属，程序集是代码边界，二者不要求一一对应；opening、title、configData、正式内容、公共字体及程序集资源可以分别分组。
- `configData` 独立组使用 Pack Separately，便于单表变化只影响对应 Bundle。公共字体独立分组；Opening 只依赖所需基本英文字体，登录阶段其余字体按实际字符覆盖及 Fallback 需求加载。
- 自动登记只能处理已确定归属；不得将 ConfigBin 自动改回 title，不得覆盖人工明确的 Group。每次改组同步检查真实构建依赖，不能只看 Addressables 视图中的显式条目。
- opening/title 不得通过字体、图集、控件或脚本加载流程提前拉取 default/Main。跨阶段复用的小型 UI 图可按审核后的加载边界拆分复制，不把整张正式内容图集拖入登录依赖；复制和引用替换须作为完整资源迁移处理。

默认启动顺序：

1. 底座建立核心服务，取得包内底座标识和项目入口地址。
2. 读取发布入口与匹配清单，安装地址映射，再初始化 Addressables。
3. 装载必要 AOT 补充元数据、Login DLL；登录入口读取并应用本地设置，再启动界面流程。
4. Opening 播放自身演出，并预加载 title 中登录表现所需资源；不加载 Main 或正式内容资源。
5. 打开 LoginPanel 时全量加载 configData，全部成功后统一初始化 Luban Tables；配置就绪前不得进入依赖配置的后续流程。配置代码必须位于此时已可用的程序集，不得反向依赖 Main。
6. 选择进入正式内容后，由 LoadingControl 排队组织 Main DLL 与正式内容资源加载；相互独立的工作可并行。全部成功后调用 Main 入口，再打开正式内容界面。

配置表批次并发上限当前采用 4，AOT 下载批次并发当前采用 3；这两个值是起点，调整时核对耗时、内存和真机表现，不能依据插件提示盲目扩大。配置就绪、DLL 就绪、依赖下载完成与界面创建完成分别记录。

## 三、底座版本与内容版本

- 底座版本标识写入包内独立启动配置，同时记录可配置的 `bootstrapUrl`。业务代码不硬编码“最新内容版本”。客户端只选择与自身底座标识完全匹配的发布项，缺失或重复匹配须报错。
- 重建底座产生新底座标识；仅发布兼容内容保留底座标识、产生新内容版本。版本目录不可覆盖，不使用 `initial/update` 区分首次与后续内容。
- 构建阶段明确选择底座构建或内容构建，并执行相应兼容性检查；不能声称脚本能自动判断所有语义兼容性。缺少匹配底座产物或已知兼容证据不足时，不得以成功编译 DLL 作为兼容证明。
- 不人工填写 PlayerSettings.bundleVersion 来控制 Catalog 名称；底座、内容及 Catalog 标识由构建协议管理。不得把样例的版本号、时间戳格式或资源文件名写死为其他工程的实例数据。

以下变化需要评估并在涉及包内内容或 AOT 能力时重建底座：

- Foundation、其他 AOT 程序集或其对业务暴露的接口发生变化。
- 业务新增对已裁剪类型、方法、未预备泛型实例、桥接能力等的依赖；现有底座无法支持时必须重建。
- Unity、HybridCLR 运行时、原生插件、微信转换插件或影响 AOT 的包版本、编译宏、裁剪设置发生变化。
- 微信包内 JS、缓存规则、启动配置、wasm/首资源包、分包声明、权限或其他包内平台配置发生变化。

仅业务 DLL、远端配置和资源变化，且仍兼容已有底座时，执行内容发布。是否需平台审核按届时平台要求单独判断，底座兼容性不是平台审核豁免判据。

## 四、远端目录与清单协议

```text
<共享 CDN 根>/
└── <项目名>/
    ├── bootstrap.json
    └── <底座版本>/
        ├── current.json
        ├── bundles/
        │   └── <保留相对子目录的哈希命名 Bundle>
        └── releases/
            └── <内容版本>/
                ├── manifest.json
                ├── settings.json
                └── catalog.json
```

- `bootstrap.json` 的 `bases` 按 `baseVersion` 映射到 `manifestUrl`，后者解析到该底座的 `current.json`。
- `current.json` 记录当前发布的 `baseVersion`、`release`、`resourceRoot`、`bundleRoot`、`aot` 和 `assemblies`；`resourceRoot` 为 `releases/<内容版本>/`，`bundleRoot` 为 `bundles/`，相对 current 地址解析。版本目录内的 manifest 保存该次不可变发布记录。
- 客户端在第一次 Addressables 初始化前，将 RuntimePath 下的 settings/Catalog 请求映射到内容版本目录，并将 Catalog 中约定的虚拟 Bundle 根映射到同底座共享 bundles 根。只替换已知前缀，保留完整相对路径，不改写无关 URL。
- Catalog 精确描述本次内容使用的 Bundle；客户端不扫描目录、不按时间挑选文件。同一底座未变化 Bundle 保持相同 URL，变化 Bundle 使用新哈希名称。
- 同名 Bundle 已存在时校验内容哈希，一致才复用，不一致立即失败，禁止覆盖。不同底座目录独立保留，不假定能够跨底座复用。
- 发布先上传并验证全部不可变产物，再更新可变发布指针。首个底座需建立入口映射；仅内容更新不必改变入口中的底座身份。
- 历史版本及其 Bundle 默认保留。回退只切换到兼容且完整的历史内容；清理必须覆盖所有保留 Catalog 的引用以及仍可能运行的旧客户端，禁止按文件年龄直接删除。
- 正式 CDN 根通过项目配置提供；模板不携带开发者盘符、IP、域名或 AppID。GitHub Pages 可作为测试承载，正式承载方式与构建系统分别配置。

## 五、settings、Catalog 与微信 DATA_CDN

- `settings.json` 是 Addressables 运行时初始化数据，包含 Catalog 定位及 Provider 等信息；全部 Group 设为 Remote 不代表它自动消失或初始化流程可以省略。
- 本策略由启动映射从远端读取 settings 与 Catalog，不依赖重复部署的 StreamingAssets 目录。是否还存在其他外置 StreamingAssets 内容须按实际项目检查，不能无条件删除所有 StreamingAssets。
- 本策略关闭 Build Remote Catalog，启用 Disable Catalog Update on Startup，由发布清单和版本目录选择 Catalog；不生成或使用 `catalog.hash` 更新依赖。该组合仅适用于本文完整启动协议，不是所有 Addressables 项目的通用设置。
- 微信转换插件的 DATA_CDN 管理插件自身的远端首资源包和外置 StreamingAssets 等请求；Addressables Remote LoadPath 管理资源定位。两者职责不同，不得将设置其中之一视为另一项自动正确。
- 首资源包在小游戏包内且没有需要外置访问的内容时，DATA_CDN 不再承担这些下载，不代表可以随意删除插件字段。按插件版本及实际产物验证，不能仅凭字段名称推断加载行为。

## 六、缓存及验证

| 内容 | 当前策略 |
|---|---|
| bootstrap/current | 可变入口，不进入客户端 SDK 持久缓存，读取时确保可取得新发布 |
| manifest/settings/hash | 当前不进入 SDK 持久缓存；本策略不通过 hash 更新 Catalog |
| 版本目录下的 Catalog | URL 随内容版本变化，允许真机缓存 |
| 同底座哈希命名 Bundle | 不可变、稳定 URL，允许真机缓存与跨内容版本复用 |

- 开发者工具按已验证的兼容策略处理缓存，与真机可有差异；不得用开发者工具的缓存统计替代真机验证。
- 缓存白名单同时限制项目/目录结构及文件身份，不能只按 `.json` 或 `.bundle` 扩展名放行所有地址。规则运行于微信包内，修改后需要更新底座。
- 服务端/CDN 缓存也须保证可变入口能及时更新；客户端“不缓存”不能证明 CDN 没有返回旧指针。
- 验收检查最终实际请求 URL、版本标识、缓存命中与新内容行为：真机保留缓存连续启动两次，再发布兼容新内容并重新启动，确认业务版本更新且未变化 Bundle 仍可复用。
- 插件关于 Catalog 无 hash/版本的建议需结合目录版本与实际请求判断，不能直接视为更新失败，也不能仅因启动变快宣称全部缓存命中。
- Addressables、DLL、HTTP 可访问性、发布完成与真机验收是不同结果，分别记录；错误日志必须能定位阶段及所选版本。

## 七、构建与开发协作边界

- 工程侧维护运行时加载器、平台配置和协议；构建侧负责目标平台编译、DLL/AOT 产出、Addressables、微信导出、兼容性检查及发布。构建发布脚本与 Jenkins 后续独立维护，必须遵守同一协议。
- 协议变化同时检查客户端和脚本版本；需要重建底座时不能只发布远端内容。常规执行构建与修改构建机制分开处理。
- 不并发操作同一 Unity 编辑器构建队列或同一发布指针。交接记录源代码版本、目标平台、底座与内容版本、产物位置、验证结果及待完成事项。
- `build`、`HybridCLRData`、Library 等可再生产物进入 Git 忽略；与底座绑定的 AOT/桥接及构建信息另行归档，不能以“已忽略”为理由丢失历史底座所需产物。源码、程序集定义、平台配置与必需元文件仍按来源管理。
- 模板不包含样例的已编译 DLL、补充元数据、微信产物或 CDN 数据副本。模板选择微信平台时应生成符合本规范的工程，迁移完成前不得把普通模板导出宣称为完整微信链路验收。
