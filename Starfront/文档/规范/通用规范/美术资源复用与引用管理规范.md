# 美术资源复用与引用管理规范

状态：现行。确认日期：2026-11-12。依据：用户确认培养与阵容同源立绘统一引用、清理重复文件，并要求据此建立资源管理规范。适用于本项目图片及其Unity导入/加载引用；不改变具体美术造型、显示尺度或资产批准范围。

## 1. 用途与实际资源分开管理

- 业务/展示用途字段可以不同，字段不同不要求复制图片。同一图片服务培养、阵容、队伍编辑等用途时，各字段应指向同一个权威资源地址，复用同一Unity资产与GUID。
- 资源目录与文件名不成为复制依据；已有portrait等名称允许继续作为权威资产，不为了用途名称对称再保存formation副本，也不为本次去重顺便重命名全部资产。
- 显示尺寸、容器、缩放、裁切、状态材质、颜色与界面布局由各消费端按既有规则控制；不得为每个显示尺寸复制同像素文件。形象一致且导入契约兼容时优先使用同一Sprite；单独的运行实例和RectTransform不属于素材重复。
- 资源由明确的配置/资源键解析，消费者不得按卡牌名称或用途自行拼接新路径。共享替换更新唯一权威资源，并复核所有实际消费端。

## 2. 合并前检查

同时核对像素/透明度/画布、文件哈希、Sprite裁切与Pivot、Pixels Per Unit、色彩空间、过滤/压缩、平台覆盖、导入模式、边界及其他实际影响显示和加载的设置。比较时区分GUID、spriteID、internalID等身份字段与显示契约。

仅PNG同SHA或肉眼相同不充分；参数不同须先说明目的，不强行合并。材质/Shader、动态状态和消费端布局也须核对，不以资源去重改动已批准的锚点、比例或外观。

## 3. 合法派生资源

允许因真实不同的构图、视角、像素内容、透明/裁切结果、明确需要的导入模式/平台约束等保留独立派生资源。记录来源、生成/处理方式、差异、实际使用端和必要性；仅用途不同、文件名不同、未来可能修改，不足以新建相同副本。

不同用途的语义锚点如确实不兼容，先按专项规范确定视图适配或派生方式，不悄悄统一Pivot。牌库卡面、碎片近景、场景单位或动画帧不因同角色就被认定与立绘相同。

## 4. 地址和生命周期

保留用途字段兼容时，多个字段可引用同一完整地址；不为别名复制文件或重复登记不同资产。Addressables以唯一实际资产/GUID登记，资源管理器按权威地址去重加载并维护多使用者生命周期。禁止某个使用端关闭时销毁仍被其他使用端使用的共享资源。

去重不新增第二套加载器，不以文件系统硬链接/软链接掩盖Unity双GUID资产，不通过拷贝/重命名制造“共用”的假象。

## 5. 迁移与清理

1. 锁定授权范围和唯一权威资产；列出源表、生成配置、Prefab/Scene/材质直接GUID、Addressables及有效代码地址引用。
2. 获准清理后，先完整归档重复PNG/meta、旧源表/生成数据及资源登记，记录原位置、哈希和恢复步骤；验证备份可读且逐字节一致。
3. 先改权威源表并通过项目原生成器更新；核对差异只在批准范围，禁止只手改生成JSON或顺带覆盖其他修改。
4. 在独占工程/编辑器时段迁移引用并移除旧登记。清理前再次确认旧GUID/路径没有剩余有效引用；档案/历史证据保留旧路径并标迁移，不做全盘替换。
5. 删除前验证每个解析后的绝对目标仍在明确批准的资产目录；只处理清单内文件，保留权威PNG/meta/GUID。Unity资产优先通过AssetDatabase删除并刷新，不能仅删PNG遗留meta或反向删除权威图。
6. 验证配置/依赖存在、共享加载身份、异步加载及关闭回收，并逐消费端验证显示与返回/重开。报告技术验证、实际运行和用户阶段验收，不能仅凭磁盘节省宣称显示不变。

## 6. 证据与维护

保留唯一资源→用途字段→实际消费端的映射、必要派生差异、迁移前后清单、归档哈希及运行证据。节省磁盘字节与GPU内存实测分别报告，不能用PNG大小推断内存收益。新生产/接入先查已有权威资源再生成或复制，发现重复先审计再按授权迁移。
