# 工作文件迁移与清理规范

状态：现行。确认日期：2026-11-02。依据：用户确认工作目录管理、迁移及清理原则，并要求进规范。适用于项目制作与交接工作文件；不替代正式资产删除、发布或源码变更的专项要求。

## 1. 名称与路径迁移

1. 区分项目显示名、实际工作路径、正式工程路径、技术标识和资源地址；改一个不默认改其余项。
2. 操作前核对源和目标绝对路径、目录存在性、目标冲突及链接属性；不覆盖同名目标，不递归操作未经核实的计算路径。
3. 迁移完整保留素材源、元数据、清单与需要保留的隐藏文件；抽查或按本次范围逐文件比对哈希，记录迁移前后位置及未核验范围。
4. 更新当前交接入口、有效执行配置、活动脚本及应用项目目录关联。应用关联以实际设置/访问结果为准；仅能确认文件可访问时，不宣称应用绑定已验证。
5. 历史日志、旧验收及备份保留原路径并提供迁移映射，不全目录盲目替换。历史脚本恢复使用时按实际依赖修复；不能因旧路径失效重新生成已通过素材。
6. 迁移后检查当前入口、有效链接、目标文件和关键依赖；确认旧目录无剩余内容后才移除空目录。正式Unity资源迁移仍遵守GUID及引用要求。

## 2. 清理分类

1. 可重建缓存：Python字节码、临时验证工程缓存等。虚拟环境删除前保存依赖版本和必要的解释器信息；node_modules等需区分真实目录、链接及可重建依赖。
2. 历史候选与备份：检查正式成果、跨版本脚本和素材来源依赖，必要时先归档。版本号旧、文件名含backup/failed或题材词，不足以单独证明可以删除。
3. 必须保留：仍被工程或流程引用的资源、唯一源视频/分层文件、已验收素材、制作脚本、定位与播放数据、正式交付及必要证据。旧动作在代码迁移和引用归零前不按新规范直接删除。
4. Git元数据单独处理：先核对提交、远端、索引及对象状态；没有提交不等于没有暂存内容。移除.git须用户明确授权，不能当普通缓存顺带清理。
5. 无法读取、链接指向不明或引用检查未覆盖的项列为未核验，不记为可删。

## 3. 执行与记录

1. 在用户已授权范围内执行；先明确具体目标及保留范围，不将某批确认扩大为全部历史文件删除授权。
2. 删除或递归移动前核验最终绝对路径位于指定工作目录内；检查链接，禁止跨链接递归清理。遇目标冲突、范围变化或校验失败停止受影响操作。
3. 清理前记录路径、文件数量、体积和判断依据；需要的依赖清单先落盘。不把密钥、令牌或凭证写入记录。
4. 完成后确认指定目标已移除、保留内容未被误动；迁移文件核对内容一致性。报告实际清理量、保留内容和未完成项，不把顶层名称检查说成全文件完整性检查。
5. 清理清单及迁移记录保存在项目交接记录目录；当前入口仅保留简短摘要与链接，不复制正式规范正文。

## 4. 生效与范围

本篇统一工作文件迁移与清理方法，具体项目路径见当前交接入口，个人默认根目录见对应个人目录约定。不包含本轮新的迁移、素材删除、构建、发布或Git操作授权。历史清理记录保留当时范围与验证事实，不追改为全面审计通过。
