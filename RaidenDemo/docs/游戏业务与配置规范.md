# 游戏业务与配置规范

## Luban 导表入口

1. 当前工程的 JSON 配置必须通过 `Project/ConfigResource/gen_json.bat` 导出。
2. 必须从 `Project/ConfigResource` 作为工作目录调用脚本。
3. 禁止绕过脚本，自行拼装、复制、推测或直接执行 Luban 命令行参数。
4. 自动化执行时，可以非交互方式处理脚本末尾的 `pause`，但不得修改脚本的参数、输出目录、生成目标或数据格式。
5. 脚本缺失、执行失败或无法满足需求时，必须先报告问题并确认脚本调整方案，不得临时改用自拟命令导表。

## Luban 配置表格式

1. 表格顶部用于定义字段、类型、说明及嵌套关系的区域统一称为“表头定义区”，其后为“数据区”。
2. 同一张表的字体和字号必须全表统一，包括表头定义区、数据区、新增列及 Bean 展开区域。
3. 表头定义区以行为单位统一样式：同一有效行的背景色、字色必须一致，Bean 展开或合并区域不得形成局部异色。
4. 单元格以列为单位统一水平、垂直对齐方式，默认均为居中；资源路径等特殊列需要例外时，必须整列统一。
5. Bean 按字段层级展开并合并父级标题；`list,Bean` 使用多行结构，字段名前加 `*`，元素字段在下一层 `##var` 行展开。合并区域只在左上角保存内容。
6. 复制合并区域格式时，禁止从合并区域的中间或末尾单元格取样；必须从相同语义区域的左上角单元格继承。字段行、说明行、子字段行和数据行应分别从同类单元格继承格式。
7. 所有有效表头行、数据行及列表延续行必须具有与原表一致的明确线框；空白预留行不作要求。
8. 修改后必须同时检查字段内容与实际格式，至少核验：背景色、字色、字体、字号、水平/垂直对齐、合并范围、线框、列宽、下拉框及文本格式；不得仅以 Luban 导表成功作为格式验收依据。

## 碰撞形状配置核验图

1. 新增或调整飞机、子弹等实体的碰撞形状后，应生成一张核验图供人工验收。
2. 核验图必须以实体原图为底图，按原图坐标与尺寸等比例叠加碰撞形状；碰撞形状使用醒目的绿色线框，不以半透明色块遮挡原画细节。
3. 核验图必须标出实体原点，并提供简短图例，明确绿色线框与原点各自代表的含义。
4. 多碰撞形状必须同时展示，并标注每个形状的用途或尺寸，确保能直观看出形状与机身可见区域的对应关系。
5. 核验图只用于配置评审与调试，不作为运行时美术资源，不得加入 Addressables。

## 场景管理架构

1. 战斗、关卡等场景业务应作为独立模块组织；`Model/VO` 是场景数据的唯一真相，`View/Presenter` 只负责视窗内表现的创建、同步与回收，不承载或复制业务规则。
2. 所有场景元素继承统一基类，创建时必须具有稳定唯一 ID 和明确的 Timer 类型。VO 只保存逻辑数据，不得持有 `GameObject`、`Transform`、`RectTransform`、`Image` 等表现对象。
3. 场景元素的移动、转向、战斗行为和生命周期由自身通过继承或组合负责。外部系统只协调波次、碰撞、查询等整体流程，不得以集中式 Logic 或 Panel 接管单个元素行为。
4. 场景逻辑统一由 Timer 消息驱动，不得直接读取 `Time.deltaTime`。玩家、敌方和中立场景元素分别使用 `playerTimer`、`enemyTimer`、`sceneTimer`；场景外逻辑默认使用通用 Timer。
5. Model 按 Timer 类型集中订阅并向对应元素派发时间增量，避免每个元素独立注册监听。暂停、分组变速和子弹时间统一通过 Timer 控制。
6. 逻辑生命周期与视窗生命周期必须解耦。元素离开视窗后逻辑仍可运行；View 的创建、隐藏或回收不代表逻辑元素生成或销毁。
7. 输入与界面操作只能向 Model 提交命令；Model 完成权威状态变更后通过事件通知 Presenter。View 不得直接修改 VO。
8. 场景单位原则上根据移速连续改变坐标，除非玩法明确设计瞬移能力，否则禁止直接跳变位置。
9. `view` 只放表现对象，`factory` 和 `pool` 负责对象创建与复用，`model/vo` 管理权威数据和元素行为；常量类使用 `{Module}Const` 命名。
10. 不创建空 Model、无独立职责的 Runtime 或单纯转发的包装类。一个文件只定义一个同名顶层类型；类注释使用简短 `summary` 概括角色，并以 `remarks` 说明职责范围。

## 场景资源预加载

1. 进入关卡前必须从关卡配置递归收集本局可预知的飞行物、发射器、子弹、命中特效和死亡特效资源，去重后统一预加载。
2. 配置能够确定的资源不得推迟到战斗中首次使用时加载；依赖缺失应在进入关卡前明确报错。
3. 依赖收集器只负责遍历配置和生成资源清单，不承担资源加载或玩法逻辑。

## 场景系统与生命周期

1. 碰撞系统只负责检测并返回碰撞事实；Model 负责伤害、死亡等权威状态变化；Presenter 根据结果播放命中和死亡表现。
2. Timer 与事件监听必须成对注册和注销；战斗退出时清理 Model、Presenter、异步回调和对象池占用。
3. 池化 View 再次使用前必须重置坐标、旋转、显隐、透明度、动画和其他可变状态，禁止继承上次生命周期的表现。

## 临时测试与重构验收

1. 临时等级、血量、跳过波次等测试改动必须集中标识；恢复正式数据时同步恢复配置测试，不得保留针对临时值的断言。
2. 提交前检查临时配置、调试入口和测试断言是否一致，不得以删除失败断言代替恢复正式状态。
3. 重构完成不能只依据文件拆分或代码行数，必须确认权威逻辑已进入 Model/VO、表现引用已离开逻辑对象、冗余包装类已删除。
4. 场景架构调整后至少执行顶层类型检查、C# 编译和核心战斗流程验证。
